# 100 个相似 GitHub 仓库：Murmur 功能路线调研

> 状态：调研提案｜适用：定位落地后的功能决策｜核验：2026-08-29｜依据：100 个公开 GitHub 仓库的一手材料与 Murmur 当前代码/现行文档；不代表功能承诺或生产验收

## 结论先行

Murmur 后续最值得做的不是扩成相册、通用知识库或 AI 角色平台，而是补齐一条可信的私人回忆闭环：

1. **素材仍是素材。** 照片、讲述、语音和聊天先保留原始含义。
2. **AI 只提出表达。** 草稿必须标明来源，允许编辑、放弃。
3. **用户确认才成稿。** 只有明确保存的内容进入“日记成稿”。
4. **留下来的东西可查、可改、可带走。** 记忆有来源，检索能回到原文，导出和删除可验证。

100 个样本中，最稳定的共识不是某一种 AI 技术，而是用户对数据位置、原始材料、修改权和退出路径的控制。按平衡路线评分，前三项是：**确认后成稿（95）**、**可验证导出与删除收据（91）**、**语音讲述转可编辑素材（90）**。

## Murmur 当前基线

本报告以 [当前能力](../product/current-state.md)、[路线图](../product/roadmap.md)、[术语](../../CONTEXT.md)、[系统边界](../architecture/system-boundaries.md) 和 [数据生命周期](../architecture/data-lifecycle.md) 为准，并与当前 iOS、Android、服务端代码交叉检查。

- iOS 已有照片/文字交流、SSE、重试、本机聊天恢复，以及“当年今日”和独立照片房间存档。
- 服务端已有邀请与身份、短期作业、服务端私有记忆、dossier、开环、连续性和主动推送。
- Android 是 Debug 开发骨架，正式认证、推送和体验对齐尚未完成。
- 尚未实现：日记草稿/确认成稿、用户可选表达风格、用户逐条管理服务端记忆、客户端历史查询、日记导出。
- 聊天记录、照片房间存档、服务端记忆和日记成稿继续是四种不同对象；本调研不改变现有 HTTP/SSE wire 契约。

## 调研方法与样本质量

### 分层样本

| 类别 | 数量 |
|---|---:|
| 日记、反思与情绪记录 | 25 |
| 照片回忆、时间线与纪念日 | 20 |
| 个人记忆、知识库与长期检索 | 20 |
| AI 陪伴与对话式回顾 | 15 |
| 语音记录与自动整理 | 10 |
| 隐私、本地优先、导出与数据主权 | 10 |
| **合计** | **100** |

纳入对象必须是公开、可检查实现的产品或服务；排除 fork、镜像、教程、空概念和纯组件。状态按 2024-08-29 之后是否仍有提交或 release 判断，并同时检查维护者声明：例如 [Pixy](https://github.com/mrzmyr/pixy-mood-tracker-app) 虽满足日期阈值但 README 已声明停止维护；[Reor](https://github.com/reorproject/reor) 已归档但最后推送仍在阈值内，两者均在表中明确披露。

每项能力只采用仓库 README、源码、release、issue 和 LICENSE 等一手材料。四批各复核 5 个样本，共人工复核 20/100；此外对进入近期/中期路线的代表仓库再次检查了确认写入、来源引用、语音隐私、导出恢复、记忆控制和主动触达机制。许可证记录仅用于识别复用风险，不构成法律意见。

### 重复模式

各批按显式能力编码；不同类别的定义存在轻微差异，因此“至少”表示保守下限。

| 模式 | 频次 | 对 Murmur 的意义 |
|---|---:|---|
| 本地、离线、自托管或用户控制主要存储 | 90/100 | 隐私不能只靠口号；产品必须逐环节说明什么在设备、什么上服务端、什么会给模型。 |
| 导入、导出或可恢复备份 | 至少 51/100 | 长期回忆需要退出路径；导出/恢复应是基础能力，而非高级功能。 |
| 明确的日期、日历或事件时间线 | 至少 29/100 | Murmur 已有“当年今日”；新增价值应是可确认的事件素材包和成稿，而不是再做一套时间线。 |
| 搜索、查询、过滤或语义召回 | 至少 38/100 | “找回”是长期价值来源；结果应回链原始聊天、照片房间或确认稿。 |
| AI 作为索引/检索/整理层，而非最终事实 | 至少 20/100 | 机器输出应可解释、可纠正、可关闭，不冒充用户记忆。 |
| 加密、设备锁或零知识设计 | 至少 17/100 | 必须区分设备锁、静态加密、传输加密、E2EE、密钥恢复和元数据暴露。 |
| 社交分享、多人协作或公开链接 | 至少 21/100 | 虽然常见，但与 Murmur 的邀请制私人回忆定位冲突，不应因竞品频繁出现而跟进。 |
| 主动触达带开关、意图或预算门槛 | 至少 5/15 个陪伴项目 | 主动消息必须可关闭、受频率和欢迎度约束，不能靠情绪施压维持留存。 |

## 建议路线

### 近期：建立可信的成稿与退出闭环

| 功能 | 用户场景与 MVP | 涉及端 / 依赖 | 隐私与边界 | 工作量 / 成功指标 | 参考 |
|---|---|---|---|---|---|
| **确认后留存的日记草稿** | 在一次照片房间或讲述后，用户主动点“整理成一页”；AI 生成带来源的候选稿，用户可编辑、保存或放弃。旧聊天/照片存档不迁移成日记。 | iOS + Server；新增独立日记领域对象和幂等接口，原 SSE 契约保持不变 | 只使用用户明确选中的素材；保存前不称为日记；保留素材与成稿的来源关系 | M；100% 草稿都有保存/编辑/放弃的显式结果，零自动成稿 | [murmur-io/murmur](https://github.com/murmur-io/murmur)、[Journiv](https://github.com/journiv/journiv-app)、[DailyTxT](https://github.com/PhiTux/DailyTxT) |
| **语音讲述转可编辑素材** | iOS 先提供按住或轻点录音；显示录音/转写状态，转写结果先进入可编辑输入框，再由用户发送或拿去成稿。支持专有名词词典；默认不长期保留原音。 | iOS 优先；首版优先系统端侧转写，能力不足时明确提示外部处理；Android 在体验确认后对齐 | 不把自动翻译当原文；提交前不上传；原音保留策略单独可见 | M；完成率、转写后人工修改率、失败恢复率；任何失败不丢原音或已得文本 | [DailyVox](https://github.com/intrepidkarthi/dailyvox)、[FlowFlow](https://github.com/mirkobozzetto/flowflow)、[shower-thoughts](https://github.com/kilsekddd/shower-thoughts) |
| **可验证导出与删除收据** | 从“我的”导出 Markdown/JSON 清单：聊天、照片房间、确认稿、附件引用和服务端记忆分别列出；删除账户后展示已删除范围与本机仍需清理的内容。 | iOS + Server；复用现有账户擦除锁，增加只读导出和范围清单；不得把“清空聊天”等同账户擦除 | 导出包不默认包含原相册照片；敏感包由系统分享面板交给用户；收据不保留正文 | M；测试导出可解析且条目数与来源一致；删除后所有服务端派生物验证为零 | [osxphotos](https://github.com/RhetTbull/osxphotos)、[TiddlyWiki](https://github.com/TiddlyWiki/TiddlyWiki5)、[Joplin](https://github.com/laurent22/joplin) |

### 中期：让长期记忆可见、可查、可控

| 功能 | 用户场景与 MVP | 涉及端 / 依赖 | 隐私与边界 | 工作量 / 成功指标 | 参考 |
|---|---|---|---|---|---|
| **记忆清单与纠错** | 用户查看 Murmur 当前认为重要的简短事实，看到来源和更新时间，可纠正或“让它忘掉”。不暴露 dossier/open-loop 等内部结构。 | iOS + Server；在现有唯一记忆源之上加审阅 API、来源标识和幂等删除 | 删除需覆盖派生索引；纠正保留审计关系但不继续召回旧值 | L；100% 可见记忆有来源，纠正/删除后下一轮不再使用旧值 | [LettuceAI](https://github.com/LettuceAI/app)、[Mem0](https://github.com/mem0ai/mem0)、[Supermemory](https://github.com/supermemoryai/supermemory) |
| **带来源的历史查询** | 用户按关键词、日期、人物或照片提问；首版先做确定性过滤/全文搜索，再按需要叠加语义召回；结果可跳回原聊天、照片房间或确认稿。 | iOS + Server；需要新的只读历史查询边界，但不变成聊天历史全量同步接口 | 回答必须引用来源；找不到时明确拒答；未经确认的聊天结果不显示成“日记” | L；来源点击率、无来源回答率为零、错误召回人工抽检 | [Reor](https://github.com/reorproject/reor)、[Khoj](https://github.com/khoj-ai/khoj)、[Sard](https://github.com/AbdulrahmanAlaasi/sard) |
| **多照片事件素材包** | 用户从同一天或一次旅程中手动选 2–4 张照片，每张可移除；AI 只基于选中照片和讲述提出事件角度，再进入草稿确认。 | iOS + Server；需要多附件作业、总大小预算、部分失败与重试语义 | 不后台上传相册；人物/地点/语义标签只做候选且可纠正 | M–L；多图任务完成率、用户移除/纠正率、单张回退成功率 | [Immich](https://github.com/immich-app/immich)、[Memories](https://github.com/pulsejet/memories)、[June](https://github.com/DenserMeerkat/June) |
| **可选表达风格** | 提供当前默认风格及少量经验证的替代风格；预览同一事实在不同表达方式下的差异。风格只影响语气、篇幅和提问方式。 | iOS + Server；用户偏好存储、提示词版本和回归评估 | 风格不能修改人物、时间和事件事实，也不冒充真人或专业治疗者 | M；事实一致性测试通过，风格切换后满意度提升且无事实差异 | [Yumii](https://github.com/CodeNeuron58/Yumii)、[Haven](https://github.com/amarisaster/Haven)、[AIRI](https://github.com/moeru-ai/airi) |
| **用户确认的周/月回顾** | 用户主动开启后，系统只从确认稿和明确允许的素材生成一页回顾；通知只提示“有一份候选回顾”，打开后仍需编辑/保存/放弃。 | iOS + Server + Worker/Push；依赖确认稿、时区、幂等调度和频率设置 | 默认关闭；安静时段和频率可调；不因缺席制造愧疚，不引用未确认私密对话 | L；退订率、通知打开后完成率、重复/越界引用为零 | [YuriOS](https://github.com/yuri-os/YuriOS)、[Xiyu](https://github.com/xiyuailove/xiyuai)、[Yuralume](https://github.com/Yuralume/yuralume-core) |

### 探索：先做原型和用户验证

| 方向 | 最小实验 | 前置与停止条件 |
|---|---|---|
| **私密回忆星图/时间视觉化** | 只用确认稿生成无精确地名的光点/月份视图；点开仍回到原文，不给情绪打分。 | 依赖确认稿和稳定查询；若用户只把它当装饰、不能提高回看率则停止。参考 [DailyVox](https://github.com/intrepidkarthi/dailyvox)、[Logseq](https://github.com/logseq/logseq)。 |
| **记忆冲突与版本化** | 当新说法与旧记忆冲突时，不静默覆盖；显示来源，让用户选“现在如此”“两者都保留”或删除。 | 依赖记忆清单与来源模型；若冲突误报过高或需要暴露复杂内部结构则不推进。参考 [Mem0](https://github.com/mem0ai/mem0)、[Supermemory](https://github.com/supermemoryai/supermemory)。 |
| **端到端加密跨设备同步** | 先做威胁模型和可恢复原型，不碰现有生产数据；验证确认稿/本机存档的密钥恢复、冲突和设备撤销。 | 必须先决定服务端记忆哪些能力可失去或迁移；未通过恢复演练不得宣传 E2EE。参考 [Ente](https://github.com/ente-io/ente)、[Standard Notes](https://github.com/standardnotes/app)、[Notesnook](https://github.com/streetwriters/notesnook)。 |

## 明确不建议

- 不做公开动态、社交 feed、公共相册或以分享卡驱动增长。
- 不做多角色市场、角色卡导入、AI 恋爱养成或“自主生活”叙事。
- 不把聊天、照片房间存档、自动摘要直接升级为日记成稿。
- 不持续采集屏幕、精确位置、健康、音乐或整库相册；派生标签也必须先审后存。
- 不建设完整照片云、通用 PKM、插件市场、团队协作或 agent 工具平台。
- 不默认用情绪分数、连续打卡、未记录惩罚或关系压力制造留存。
- 不为“隐私优先”口号仓促加入 E2EE；它会重塑现有服务端记忆、检索、恢复和推送契约。
- 不把 source-available、非商业许可证或 README 宣称等同于可直接复制实现。

## 实施顺序与工程门槛

1. 先完成邀请制体验的真实设备可靠性：App Attest/APNs、Android 正式认证/FCM、上传恢复和生产观察仍是功能扩张前置。
2. 以“确认后成稿”定义新领域边界，再接语音、多图、回顾，避免它们落进聊天或照片房间旧语义。
3. 导出/删除先定义数据清单与恢复测试；记忆清单和历史查询复用现有服务端记忆，不创建第二套真相源。
4. 每个新 API 保持认证失败关闭、幂等、上传终态清理和 SSE 兼容；生产迁移与部署另行授权。
5. 每项功能先在 iOS 定义体验并完成单元/UI/真机验收，再按共享契约对齐 Android。

## 验收结果与限制

- 自动检查：**100 行、100 个唯一 canonical GitHub 仓库 URL**；类别为 **25/20/20/15/10/10**；每行均包含定位、平台、状态/许可证、功能、存储/隐私、可借鉴点、不适合点和一手证据。
- 人工检查：每批 5 个，共 **20 个随机/风险样本**；另复核所有近期和中期建议引用的代表仓库。
- 样本偏向开源、自托管和技术用户，不能代表商业应用的真实留存率或付费意愿。
- “Active”只表示公开维护活动，不等于成熟、稳定、安全或已在商店上线。
- 本轮核对仓库声明和可检查实现，没有逐个安装运行 100 个产品；任何进入实现的能力都需要单独做原型、威胁建模和用户测试。
- 历史调研仅用于发现候选，不覆盖当前产品文档；本报告本身也是提案，不自动变成待办。
